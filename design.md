# PAYAYAR --- Design System & UI/UX Rules

> **Purpose:** This document is the visual and UX contract for **پایا‌یار
> (PAYAYAR)**. Every AI coding agent must read this file before
> creating, redesigning, or materially changing UI. The goal is to
> preserve a consistent, intentional, professional product identity
> across Windows and mobile and to prevent different AI agents from
> gradually turning the interface into a generic AI-generated dashboard.

------------------------------------------------------------------------

## 1. Product Identity

### Product name

-   Persian: **پایا‌یار**
-   Latin/brand form: **PAYAYAR**

The visual identity must feel like a deliberately designed
productivity/study product, not like a template generated by an AI
assistant.

### Core feeling

The interface should communicate:

-   Focus
-   Calm
-   Progress
-   Serious study
-   Modern technology
-   Trust
-   Personal ownership

It should feel polished and premium without becoming flashy, childish,
or overly corporate.

### Important

The supplied design reference may contain a temporary visual/name such
as `PathToSuccess`. **Do not copy that product name into the
implementation. The actual product identity is PAYAYAR.**

------------------------------------------------------------------------

## 2. Reference Design Direction

The current visual direction is based on the approved concept image
provided with this project.

### Main visual characteristics

-   Deep dark-blue / midnight background
-   Subtle scenic imagery behind the interface
-   Semi-transparent glass-like surfaces
-   Soft borders rather than heavy outlines
-   Controlled glow and blur
-   Rounded cards with moderate corner radius
-   Strong visual hierarchy
-   Blue as the primary accent
-   Green, orange, pink/red, and purple used as semantic accents
-   Clean Persian typography
-   Spacious but information-efficient layouts
-   Professional charts
-   Minimal decorative elements
-   Desktop sidebar + mobile bottom navigation
-   AI presented as an integrated product capability, not as a separate
    gimmicky visual theme

The interface should feel visually layered, but **never visually
noisy**.

------------------------------------------------------------------------

## 3. Design Philosophy

### 3.1 The UI is a product, not a collection of components

Do not design every screen independently.

Pages must look like parts of the same application.

The same visual language must be shared across:

-   Home
-   Planning
-   Study
-   Exams
-   Reports
-   Lifestyle
-   AI Advisor
-   Settings
-   Dialogs
-   Forms
-   Empty states
-   Error states
-   Mobile screens

### 3.2 Consistency beats novelty

When adding a new screen:

1.  Reuse existing patterns.
2.  Reuse existing components.
3.  Reuse existing spacing.
4.  Reuse existing typography.
5.  Reuse existing color semantics.
6.  Introduce a new pattern only when the existing system cannot
    reasonably support the requirement.

Do not create a new card style just because a new page is being
designed.

### 3.3 Calm visual hierarchy

The user should immediately understand:

1.  Where am I?
2.  What matters now?
3.  What should I do next?
4.  What has already been completed?
5.  What can AI help me with?

Do not make every element visually loud.

# 5. Background & Atmosphere

The approved direction uses a scenic, atmospheric background behind the
UI.

### Desired effect

-   Darkened scenic image
-   Cool blue tone
-   Moderate transparency/blur
-   UI remains readable above the image
-   Background should feel premium and calm

### Important rule

The background is atmospheric, not content.

Text, charts, controls, and cards must remain visually dominant.

### Do

-   Use a subtle image or gradient.
-   Add a dark translucent overlay where necessary.
-   Blur or reduce contrast behind dense content.
-   Preserve readability.

### Don't

-   Use a bright/high-contrast wallpaper behind text.
-   Let scenery compete with cards.
-   Use unrelated stock photography on individual pages.
-   Change the background style randomly between screens.

### Preferred fallback

If a scenic background is not appropriate for a particular screen:

-   use the same dark color family;
-   keep the same visual atmosphere;
-   do not invent a completely different theme.

The concept uses translucent surfaces.

### Card style

Preferred:

-   Dark translucent surface
-   Subtle border
-   Soft shadow
-   Moderate blur
-   Consistent radius
-   Comfortable internal padding

Avoid:

-   Very thick borders
-   Strong neon glow
-   Heavy drop shadows
-   Excessive gradients

1.  Primary surface
2.  Secondary surface
3.  Inset / compact surface

Not every card should look identical.

# 8. Typography

The application is Persian-first.

### Primary font

**Vazir** is the primary UI font for PAYAYAR.

Use the available Vazir font weights consistently across the interface.
Preferred semantic weight mapping:

``` text
300  Light        → secondary text, subtle supporting content
400  Regular      → normal body text
500  Medium       → labels, navigation, form text
600  SemiBold     → section titles, important labels
700  Bold         → page titles, strong metrics, primary emphasis
800  ExtraBold    → major numeric emphasis when needed
900  Black        → rare, high-emphasis display text only
```

### Typography rules

-   Prefer Vazir throughout the product for a unified Persian visual
    identity.
-   Do not mix unrelated Persian font families without explicit
    approval.
-   Use different weights to create hierarchy rather than relying only
    on font size.
-   Do not use heavy weights everywhere; most UI text should remain in
    Regular/Medium.
-   Keep numeric metrics visually strong but readable.
-   Use the same weight semantics across Windows and mobile.
-   If a particular Vazir distribution does not provide one of the
    listed weights, use the closest available weight rather than
    introducing another font family.
-   Persian text must render correctly in RTL layouts.
-   Numbers, dates, percentages, and mixed Persian/Latin content must
    remain legible and visually balanced.

# 10. Corners, Shapes & Icons

### Corner radius

Use rounded geometry, but keep it professional.

Suggested conceptual scale:

``` text
Small controls      10–12 px
Cards               14–18 px
Large panels        18–24 px
Buttons             10–14 px
```

Do not make every object extremely rounded.

### Icons

-   Use one coherent icon family.
-   Keep stroke weight consistent.
-   Prefer simple line icons.
-   Avoid mixing emoji, random SVG styles, and unrelated icon packs
    inside the main navigation.
-   Semantic icons may use controlled accent colors.

### Do not overuse decorative icon boxes.

An icon should help recognition, not fill empty space.

Good uses:

-   page transitions
-   modal appearance
-   progress updates
-   navigation state

-   constant floating animation
-   excessive glowing effects
-   animated backgrounds

# 23. Design Consistency Rules for AI Coding Agents

Before changing UI, an AI agent must:

1.  Read this file.
2.  Inspect the existing screen.
3.  Identify reusable components.
4.  Preserve existing spacing, colors, typography, and interaction
    patterns.
5.  Check both Windows and mobile implications.
6.  Prefer extending an existing pattern over inventing a new one.

### The agent must not:

-   Redesign the entire app for a small UI request.
-   Replace the design system without explicit approval.
-   Introduce a new color palette casually.
-   Introduce a different typography system.
-   Add random gradients.
-   Add generic "AI dashboard" styling.
-   Replace glass surfaces with unrelated flat cards without approval.
-   Add unnecessary animations.
-   Change navigation placement without approval.
-   Make every section visually identical.
-   Copy a generic template from a UI library without adapting it to
    PAYAYAR.
-   Remove existing visual hierarchy because a framework component uses
    different defaults.

# 29. Background Image System

The scenic background is a permanent part of the PAYAYAR visual language
and must be treated as a controlled design element.

### Rules

-   The application should support a configurable background image
    behind the main UI.
-   The image must remain subtle and atmospheric, not compete with
    content.
-   Use a dark/translucent overlay when necessary to preserve
    readability.
-   Background image, opacity, blur, and overlay strength should be
    centralized in the design system/theme rather than hard-coded
    separately on every screen.
-   Preserve the same visual treatment across Windows and mobile, while
    allowing different image crops or positioning when required by the
    screen aspect ratio.
-   Do not replace the approved background direction with random stock
    images on individual screens.
-   Do not introduce animated/video backgrounds unless explicitly
    approved.
-   If the background image is unavailable, fall back gracefully to the
    same dark navy visual system.

### AI-agent rule

An AI coding agent must not change, remove, replace, or substantially
restyle the background image system during a normal UI task unless the
task explicitly requests a background change.

# 30. Visual QA & Screenshot Testing

Visual consistency and bug detection are part of the UI implementation
process.

### Before considering a UI task complete, the AI coding agent should, when the available tooling permits:

1.  Run the application.
2.  Open the affected screen.
3.  Capture or inspect a screenshot of the result.
4.  Check the screen against this `design.md`.
5.  Look for visible UI bugs and regressions.
6.  Fix discovered visual issues.
7.  Re-run the affected screen and verify the fix.

### Visual checks

The agent should actively check for:

-   Overflow and clipped content
-   Incorrect RTL alignment
-   Broken Persian text or font fallback
-   Incorrect font weights
-   Misaligned cards and components
-   Inconsistent spacing
-   Broken responsive layouts
-   Elements extending outside their containers
-   Text overlapping other elements
-   Charts being clipped or unreadable
-   Buttons or controls becoming inaccessible
-   Incorrect colors or semantic states
-   Broken glass/background effects
-   Excessive shadows, glow, or gradients
-   Mobile horizontal scrolling that was not intentionally designed
-   Windows layouts that waste space or collapse incorrectly
-   Missing loading, empty, error, or success states
-   Visual regressions caused by the current change

### Important

Screenshot testing is a verification step, not a reason to redesign the
interface.

If the screenshot reveals a problem: - Fix the smallest relevant part. -
Preserve the existing design language. - Do not redesign unrelated
screens. - Re-test after the fix.

### If automated screenshot testing is available

Prefer using it for important UI changes.

Suggested flow:

``` text
Implement
   ↓
Run app
   ↓
Capture screenshot
   ↓
Inspect / compare
   ↓
Find visual bugs
   ↓
Fix
   ↓
Capture again
   ↓
Verify
```

### If screenshot automation is unavailable

The agent should still run the application and perform the closest
available visual/manual verification rather than assuming that a
successful build means the UI is correct.

# 31. UI Bug Prevention Rules

A successful build is not sufficient evidence that a UI change is
correct.

### The agent must distinguish:

-   **Build correctness** --- the project compiles/runs.
-   **Functional correctness** --- interactions behave as intended.
-   **Visual correctness** --- the interface matches the design system.

All three should be considered before declaring a significant UI task
complete.

### Do not

-   Declare a UI task complete immediately after compilation.
-   Assume Flutter widgets will automatically look correct on every
    screen size.
-   Ignore screenshot/rendering problems because the code has no errors.
-   Fix one screen by breaking another responsive layout.
-   Hide overflow problems instead of fixing their underlying layout.
-   Replace a problematic component with a generic framework component
    without checking visual consistency.

------------------------------------------------------------------------

# 32. AI Agent UI Change Protocol

For every significant UI modification:

### Before coding

-   Read `design.md`.
-   Inspect the existing implementation.
-   Identify reusable components.
-   Identify affected Windows and mobile screens.
-   Identify whether the change affects background, typography, spacing,
    colors, navigation, or shared components.

### During coding

-   Make the smallest coherent change.
-   Reuse existing design tokens/components.
-   Avoid unrelated refactoring.
-   Preserve existing behavior.
-   Keep the background and visual atmosphere intact unless explicitly
    requested.

### After coding

-   Run the affected screen.
-   Perform screenshot/visual verification when possible.
-   Check Windows and mobile implications.
-   Fix visual regressions found during verification.
-   Do not expand the task into an unsolicited redesign.

### Completion rule

An AI agent should consider a UI task complete only when:

``` text
Code works
+
UI renders correctly
+
No obvious visual regression
+
Design system is preserved
```

------------------------------------------------------------------------

# 33. Regression Protection

When modifying a shared component, the agent must consider every screen
that uses it.

Examples:

-   Changing `GlassCard` → check screens containing cards.
-   Changing typography → check Persian text-heavy screens.
-   Changing `PageHeader` → check major pages.
-   Changing navigation → check Windows and mobile.
-   Changing background treatment → check all major surfaces.
-   Changing spacing tokens → check dense planning and schedule screens.

### Rule

Do not optimize one screen at the cost of consistency or usability
elsewhere.

------------------------------------------------------------------------

# 35. Design Tokens

All reusable visual values must come from centralized design tokens.

The agent must prefer existing tokens over creating new one-off values.

### Token categories

-   Colors
-   Typography sizes
-   Typography weights
-   Spacing
-   Border radius
-   Border widths
-   Opacity
-   Blur
-   Shadows
-   Elevation
-   Animation duration
-   Animation curves
-   Component heights
-   Touch target sizes

### Rules

-   Do not introduce arbitrary visual values when an existing token can
    be reused.
-   If a new token is genuinely necessary, add it to the central design
    system instead of hard-coding it inside a single screen.
-   Similar visual purposes must use the same token.
-   Do not create near-duplicate tokens such as several almost-identical
    spacing or radius values without a documented reason.

# 36. Responsive Layout System

PAYAYAR must be intentionally responsive rather than simply stretched or
compressed.

### Target form factors

-   Mobile
-   Tablet / narrow window
-   Desktop / Windows
-   Large desktop

### Responsive rules

The exact breakpoints should be centralized in the responsive layout
system.

The agent must define behavior for:

-   Sidebar visibility
-   Bottom navigation visibility
-   Number of content columns
-   Card stacking
-   Grid density
-   Header layout
-   Charts
-   Calendar and schedule views
-   Dialogs and sheets
-   AI assistant surfaces

### Rules

-   Do not solve desktop problems by breaking mobile.
-   Do not solve mobile problems by unnecessarily shrinking desktop
    content.
-   Prefer rearranging content over simply reducing font sizes.
-   Important information must remain accessible at every supported
    size.
-   Avoid horizontal scrolling unless it is an intentional interaction.
-   Test significant UI changes at both a desktop and mobile size.

# 38. Accessibility

PAYAYAR should follow practical accessibility principles without
compromising its visual identity.

### Rules

-   Maintain readable text contrast.
-   Interactive controls must have an adequate touch/click target.
-   Important information must not be communicated only through color.
-   Keyboard focus must be visible on Windows.
-   Interactive elements must have meaningful labels.
-   Avoid unnecessarily small text.
-   Respect user text scaling where the platform supports it.
-   Do not use animation that makes essential information difficult to
    read.
-   RTL and accessibility semantics must work together.

Accessibility improvements must be implemented through the existing
design system rather than through unrelated visual redesign.

# 39. Persian + English Localization

PAYAYAR supports **both Persian and English**.

Language must be treated as a first-class product feature.

### Language switch

The user must be able to switch between:

-   فارسی
-   English

The selected language should persist across application restarts.

### Persian mode

-   Use RTL layout.
-   Use Vazir as the primary Persian UI font.
-   Use Persian UI copy.
-   Support Persian date presentation where applicable.
-   Preserve correct rendering of Persian and Arabic characters.
-   Handle mixed Persian/Latin text correctly.

### English mode

-   Use LTR layout.
-   Use an appropriate Latin fallback/system font where required.
-   Translate UI labels, navigation, settings, states, errors, and
    system messages.
-   Do not leave random untranslated Persian strings in English mode.

### Mixed content

The application must correctly handle:

-   URLs
-   English technical terms
-   API/model names
-   numbers
-   percentages
-   dates
-   times
-   course names
-   AI responses containing mixed Persian and English

### Important

Changing language must not require rebuilding the UI manually.

The layout direction and text alignment must react correctly to the
active locale.

# 40. Dark Mode + Light Mode

PAYAYAR supports both **Dark Mode and Light Mode**.

The user must be able to switch between them from Settings or the
designated theme control.

### Modes

``` text
Dark
Light
```

If a system-theme option is later implemented, it must be added
explicitly rather than assumed.

### Dark mode

The current approved dark navy / atmospheric visual language remains the
reference design for Dark Mode.

### Light mode

Light Mode must be a genuine theme adaptation, not simply:

> dark colors → white

It must preserve:

-   hierarchy
-   spacing
-   component identity
-   semantic colors
-   readability
-   glass/surface relationships where appropriate
-   visual personality

### Rules

-   Use semantic theme tokens rather than hard-coded colors.
-   Do not create separate component implementations for Dark and Light
    Mode unless technically necessary.
-   Components should adapt through theme tokens.
-   Charts must remain readable in both themes.
-   Background imagery must be adapted with appropriate overlay/opacity
    for each theme.
-   AI surfaces must remain visually distinct in both themes.
-   Do not introduce unrelated visual redesign when implementing theme
    switching.

# 41. Empty, Loading, Error and Success States

``` text
Empty
Error
Success

```

-   No study plan
-   No exam
-   No study records
-   No sleep records
-   No lifestyle data

### Rules

-   Never show raw technical errors to the user when a friendly UI state

-   Empty states should explain what the user can do next.
-   Loading states should preserve layout stability.
-   Error states should provide a clear recovery action when possible.
-   Do not use generic English placeholders in Persian mode.

# 42. Confirmation, Undo and Destructive Actions

Important user data should not be accidentally destroyed.

### Confirmation should be considered for:

-   Deleting plans
-   Deleting exams
-   Deleting study records
-   Clearing reports
-   Resetting settings
-   Removing API configuration
-   Bulk deletion

### Rules

-   Do not add confirmation dialogs to harmless actions.
-   Prefer Undo where it provides a better experience.
-   Destructive actions must be visually distinguishable.
-   Confirmation text must clearly explain what will be removed.
-   Never silently delete user data.

# 43. Performance-Oriented UI Rules

PAYAYAR is intentionally a lightweight local-first application.

Visual quality must not come at the cost of unnecessary resource usage.

### Rules

-   Avoid unnecessary rebuilds.
-   Avoid excessive blur and expensive visual effects.
-   Do not use large background assets when an optimized asset is
    sufficient.
-   Optimize background images for their actual display sizes.
-   Avoid animated/video backgrounds unless explicitly approved.
-   Avoid unnecessary always-running animations.
-   Do not render large numbers of chart elements when they are not
    visible.
-   Prefer lazy rendering for long lists.
-   Keep UI components lightweight.
-   Do not add heavy UI libraries solely for cosmetic effects when
    native Flutter capabilities are sufficient.

### Principle

``` text
Use the simplest implementation that achieves the approved design.
```

# 44. AI Agent Design-Safety Rules

AI coding agents must treat this document as a design contract.

### Before changing UI

The agent must:

1.  Read `design.md`.
2.  Inspect the existing implementation.
3.  Reuse existing components and tokens.
4.  Identify affected platforms.
5.  Identify affected themes and languages.
6.  Identify possible regression areas.

### During UI changes

The agent must:

-   Make the smallest coherent change.
-   Preserve existing visual language.
-   Reuse components.
-   Reuse tokens.
-   Preserve functionality.
-   Preserve localization.
-   Preserve Dark/Light behavior.
-   Avoid unrelated refactoring.

### The agent must not

-   Redesign a screen without being asked.
-   Replace the design language with a generic AI-generated UI.
-   Introduce random gradients, glass effects, glow, shadows, or
    animations.
-   Change fonts without explicit approval.
-   Remove the background image system without explicit approval.
-   Add a new color palette without explicit approval.
-   Convert the entire UI to a new component style because it looks
    fashionable.
-   Change navigation structure during an unrelated UI task.
-   Remove existing states or interactions without checking their
    purpose.

### Conflict rule

If the agent's preferred implementation conflicts with `design.md`, the
existing project design takes priority unless the user explicitly
requests a design change.

# 45. Visual Regression Testing

When screenshot or UI automation is available, significant UI changes
should be visually tested.

### Minimum process

``` text
Read design.md
      ↓
Implement change
      ↓
Run application
      ↓
Capture affected screen
      ↓
Inspect screenshot
      ↓
Check desktop + mobile
      ↓
Check Dark + Light
      ↓
Check Persian + English
      ↓
Fix regressions
      ↓
Re-test
```

### Check for

-   Overflow
-   Clipping
-   Incorrect RTL/LTR
-   Font fallback
-   Wrong font weights
-   Misaligned components
-   Broken responsive layout
-   Incorrect theme colors
-   Broken background readability
-   Missing states
-   Text overlap
-   Chart clipping
-   Navigation issues
-   Unexpected layout shifts

### Rule

A successful build does not prove visual correctness.

# 46. Shared Component Regression Protection

When a shared component changes, the agent must identify and consider
all screens that use it.

Examples:

-   Card component → all card-based screens
-   Typography tokens → all text-heavy screens
-   Header → all major screens
-   Navigation → desktop and mobile navigation
-   Theme tokens → Dark and Light Mode
-   Localization components → Persian and English
-   Background component → all major surfaces
-   Chart components → all reporting screens

Do not optimize one screen at the expense of the rest of the
application.
